# 起票ルーブリック

judge がこのファイルを system prompt に埋め込む。
判定基準をここに明文化しておかないと、優先度と type が実行ごとにブレる。

## type の選び方

| ラベル | 選ぶとき |
|---|---|
| `type:bug` | 現在の挙動が意図と違う。誤った値を返す、例外で落ちる、ガードが抜けている |
| `type:security` | 脆弱性、機密情報の露出、権限設定の過大 |
| `type:test` | 挙動は正しいがテストが無い・足りない・非決定的 |
| `type:feature` | 今は存在しない機能・関数の追加要求 |
| `type:refactor` | 挙動を変えずに構造を直す。重複排除、命名、分割 |
| `type:docs` | ドキュメントの誤り・欠落・コードとの乖離 |
| `type:chore` | ビルド、CI 設定、依存更新、lockfile |

`type:` は必ず 1 つだけ選ぶ。迷ったら「読んだ人が最初に見るべき観点」を選ぶ。
例: テストが無い割り算にゼロ除算ガードも無い → ガードの欠落が本題なので `type:bug`。

## priority の選び方

| 優先度 | 基準 |
|---|---|
| `P0` | 動かない / データが壊れる / 情報が漏れる。`high` 以上の脆弱性。CI が半分以上落ちている |
| `P1` | 誤った結果を静かに返す。公開 API にテストが無い。ビルドが再現しない |
| `P2` | 保守性の劣化。重複、ドキュメント乖離、残置 TODO、非決定的なテスト |
| `P3` | あると良い程度。命名、コメント、軽微な統一 |

判断に迷ったら 1 段下げる。P0 を安易に付けると優先度が機能しなくなる。

## confidence の付け方

0.0〜1.0 で、**その指摘が実際に直すべき問題である確信度**を入れる。
コードの読みやすさに対する主観ではなく「誤検出の可能性」を見積もる。

- `0.9` 以上 — 事実として確定している (ファイルが無い、脆弱性 DB に載っている、CI ログに失敗が残っている)
- `0.6`〜`0.9` — 静的解析の結果として妥当だが、意図的な設計の可能性が残る
- `0.6` 未満 — 推測が混じる。publish 側で既定しきい値により捨てられる

意図的な仕様に見えるものは、無理に起票せず confidence を下げること。
`0.6` を下回る指摘は出さなくてもよい。**件数を稼ぐ必要はない。**

## body の書き方

起票される issue の本文になる。次の 4 ブロックを Markdown で書く。

1. **現状** — 何がどうなっているか。ファイルパスと行番号を含める
2. **なぜ問題か** — 放置すると何が起きるか。1〜3 行
3. **対応案** — 具体的に何を変えるか。コード片を出せるなら出す
4. **根拠** — signal の evidence から引いた事実

守ること:

- 日本語で書く
- 推測を事実として書かない。確認できていないことは「可能性がある」と明示する
- signal の evidence に無い情報を創作しない。行番号・件数・パスを捏造しない
- 既存の実装方針を否定する前に、それが意図的である可能性に触れる
